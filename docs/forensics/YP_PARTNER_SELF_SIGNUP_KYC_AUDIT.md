## 1. EXECUTIVE SUMMARY

This forensic audit evaluates the end-to-end partner onboarding, identity verification, Know Your Customer (KYC), and access authorization architecture across the BSDL ecosystem. 

Historically, Channel Partners were onboarded exclusively via tenant administrators in `bs_admin_portal` through `POST /api/v1/platform/onboarding/channel_partner`. Upon creation, the partner was immediately marked `status = 'ACTIVE'`, completely bypassing mandatory KYC verification, email validation, and formal administrative approval. Furthermore, the mobile application `yp_executive_mobile` functioned strictly as a **Sign-In Only** portal with no self-signup entry point, progressive onboarding stepper, or KYC document management.

This audit establishes the empirical baseline across the 8 critical system domains and outlines the technical delta required to transition to a governed **Unified Partner Lifecycle**.

## 2. FORENSIC AUDIT OF THE 8 TARGET DOMAINS

### Domain 1: Existing YP_PARTNER_APP (`yp_executive_mobile`)
* **Current State:** 
  * The presentation layer entry point (`lib/features/authentication/presentation/widgets/authentication_panel.dart`) displays only a "Welcome Back" phone number field with OTP request.
  * There is **zero self-signup CTA** (`Create Account` / `Sign Up`).
  * No views or controllers exist for identity collection, progressive profile capture, or KYC document submission (Aadhaar, PAN, Bank Proof).
  * Upon successful OTP verification, `authSessionControllerProvider.notifier.markAuthenticatedFromLogin()` immediately triggers `startupOrchestratorProvider.notifier.resetAndRun()`, loading the primary executive dashboard without checking KYC or approval state.
* **Vulnerability / Architectural Gap:** Unapproved users who possess a provisioned account immediately gain access to operational features (Leads, Referrals, Programs, Institutions) without completing verification.

### Domain 2: Current Admin Partner Onboarding (`bs_admin_portal` & `bs_api_service`)
* **Current State:**
  * Implemented in `src/application/journeys/channel_partner_journey.py` via `POST /api/v1/platform/onboarding/channel_partner`.
  * The journey resolves the tenant organization, registers the identity, provisions the workforce profile, and executes:
    ```sql
    UPDATE workforce.org_workforce_profiles SET status = 'ACTIVE', updated_at = NOW() WHERE id = :mid
    ```
  * KYC documents (`kyc_documents`) and payout profiles (`payout_profile`) are modeled as optional payloads (`Optional[List[KYCDocumentInput]]`).
* **Vulnerability / Architectural Gap:** Merely creating a partner in the admin portal automatically grants active operational status. The system lacks review queues, verification gates, or post-invitation continuation workflows.

### Domain 3: IAM & Identity Architecture
* **Current State:**
  * The identity model strictly decouples human persons from system credentials:
    * `identity.persons`: Physical individual (first name, last name, phone, email, gender, DOB, address).
    * `identity.user_accounts`: Authentication principal, status (`ACTIVE`, `SUSPENDED`), email/phone links.
    * `workforce.org_workforce_profiles`: Tenant-specific engagement (membership ID, workforce classification `CHANNEL_PARTNER`, status `ACTIVE`).
    * `workforce.org_workforce_assignments`: Department (`MARKETING` / `OPERATIONS`) and job role (`DIGITAL_PARTNER` / `FIELD_EXECUTIVE`).
    * `iam.role_assignments` -> `iam.roles` -> `iam.permissions`.
* **Alignment:** The underlying domain model is structurally robust and can support the new lifecycle without introducing duplicate user or identity tables.

### Domain 4: Tenant & Organisation Association
* **Current State:**
  * Multi-tenancy is enforced at the organization level (`organisation.organizations` with `organization_level = 'TENANT'`).
  * In the existing admin flow, `organization_id` is supplied by the authenticated admin's context.
* **Vulnerability / Architectural Gap:** Self-signup must never allow an arbitrary user to pass an unverified `organization_id` in the API payload. Doing so would enable cross-tenant data pollution and unauthorized organizational affiliation.
* **Governed Directive:** Self-signup must require a cryptographic invitation token (generated by a Tenant Admin) or an approved Organisation Partner Code.

### Domain 5: Current KYC Implementation
* **Current State:**
  * Physical database tables exist:
    * `workforce.person_kyc_documents`: Supports storage of `document_type`, `storage_bucket` (`platform-private-documents`), `storage_path`, `checksum_sha256`, and `verification_status` (`SUBMITTED`, `UNDER_REVIEW`, `VERIFIED`, `REJECTED`).
    * `workforce.member_payout_profiles`: Supports encrypted bank account storage (`account_number_encrypted`, `account_number_last4`, `ifsc_code`, `bank_name`).
  * Missing Domain Constructs:
    * No canonical `workforce.kyc_cases` table to track case status, submission timestamps, reviewer assignments, and decision outcomes.
    * Only Aadhaar document upload was supported in legacy scripts; PAN card documents and bank proof documents were not enforced.
    * No per-document correction request mechanism or resubmission state machine exists.

### Domain 6: Existing Email & Mobile Verification
* **Current State:**
  * Mobile verification is currently coupled directly with authentication OTP (`src/legacy/platform_core/identity/api.py`). Completing OTP produces a session token rather than recording an isolated `mobile_verified = TRUE` state attribute.
  * Email verification follows `docs/architecture/EMAIL_VERIFICATION_ARCHITECTURE.md`: creates an asynchronous verification challenge via the Notification Outbox. When clicked, it validates the token and marks `email_verified = TRUE`.
* **Governed Directive:** Mobile verification and Email verification must remain strictly separated and must precede KYC submission.

### Domain 7: Notification Outbox Architecture
* **Current State:**
  * Transactional outbox table: `notifications.email_outbox`.
  * Enqueued within the same database transaction as the business event via `EmailOutboxService.enqueue_notification()` with deduplication (`ON CONFLICT (idempotency_key) DO NOTHING`).
  * Supports tenant isolation via `organization_id` mapping.
* **Alignment:** 100% compliant with enterprise isolation standards. Email sending never executes synchronously within HTTP request cycles.

### Domain 8: Render Worker Daemon
* **Current State:**
  * Background worker: `SubscriptionLifecycleWorker` (defined in `src/application/workers/subscription_lifecycle_worker.py`).
  * Claims queued outbox records using PostgreSQL row-level locks:
    `SELECT ... FROM notifications.email_outbox WHERE status IN ('PENDING', 'FAILED_RETRYABLE') ... FOR UPDATE SKIP LOCKED`
  * Enforces exponential backoff across 5 attempts and moves persistent failures to dead-letter storage.
* **Alignment:** Ready for integration with partner onboarding notification events (`PARTNER_SIGNUP_COMPLETED`, `EMAIL_VERIFICATION_REQUIRED`, `KYC_SUBMITTED`, `KYC_CORRECTION_REQUIRED`, `PARTNER_APPROVED`).

## 3. EMPIRICAL GAP & REMEDIATION MATRIX

| System Domain | Current Empirical State | Target Architecture Standard | Remediation Requirement |
| :--- | :--- | :--- | :--- |
| **Mobile Entry** | Sign-In Only (`AuthenticationPanel`) | Sign-In + Create Account (Self-Signup) | Add Welcome Gate & Register flow |
| **Tenant Association** | Direct Admin Injection | Governed Invitation / Verified Org Code | Enforce token validation before account creation |
| **Identity Verification**| Bundled in session token | Separate `mobile_verified` & `email_verified` | Decouple challenges and track explicit booleans |
| **Profile Collection** | Admin-supplied fields | Partner self-service progressive profile | Collect minimum compliance data (Kerala districts) |
| **KYC Breadth** | Aadhaar only (optional) | Mandatory Aadhaar + PAN + Bank & Proof | Enforce all 3 modules on backend before submission |
| **KYC Case Model** | Non-existent | Canonical `workforce.kyc_cases` | Add table with deterministic state machine |
| **Document Storage** | Private bucket configured | Signed URL target + proxy verification | Maintain private access with time-limited signed URLs |
| **Sensitive Data Masking**| Stored plaintext / unmasked | Masked Aadhaar, PAN, Bank in listings | Implement `XXXX XXXX 1234` masking format |
| **Admin Onboarding** | Auto-activates (`status = 'ACTIVE'`) | Creates invited account requiring KYC | Gate workforce profile activation on KYC approval |
| **Admin Review** | None | Dedicated Single-Screen Review Console | Build document-level review and decision modal |
| **Correction Flow** | None (manual SQL) | Granular correction request & resubmit | Allow per-document re-upload without resetting all |
| **Access Control** | Open after OTP | Restricted to `ONBOARDING_ONLY` | Authorize operational routes only after approval |
